# AutoRoute P0–P2 开发文档

> 原始需求：「给以上P0-P2，写完整的开发文档，然后给DeepSeek-v4.1-flash去开发完成。」
>
> 本文是实现者与审查者的唯一验收基线。实现必须基于当前工作区增量修改，不得用初始提交覆盖或回滚已有未提交工作。

## 1. 产品定位

AutoRoute 是 **macOS 上 Coding Agent 的本地多模型路由与成本控制中心**，优先服务 Codex、Claude Code、OpenCode、Hermes 等本机 Agent 用户。

核心价值主张：

1. 5 分钟内完成发现模型、配置路由、接入 Agent 和真实请求验收。
2. 在工具调用、流式响应和多轮会话中稳定路由，上游失败时按明确规则回退。
3. 每笔调用的模型选择原因、路由耗时、上游 TTFT、总耗时、Token、估算费用和重试成本均可核对。
4. 本地优先：无账号、无强制遥测，供应商密钥和本地访问凭据进入 macOS Keychain，正文记录默认关闭。

### 1.1 非目标

本阶段不做：

- Windows 或 Linux 客户端。
- 插件市场、托管控制平面、账号系统或强制云端遥测。
- 为追求 API 数量而实现图片、音频、Embeddings 等泛化接口。
- 虚构 Benchmark、下载量、成本节省、签名、公证或发布结果。
- 大规模重命名 Swift module、内部类型或持久化标识符；品牌统一指用户可见名称、文档、产物和发布元数据统一为 AutoRoute。

## 3. 总体完成定义

每个代码切片必须按以下顺序完成：

1. 阅读当前实现与既有未提交差异，写明要保护的行为。
2. 添加一个能证明需求的具体测试，并在修复前观察它失败；无法安全制造红色状态时，记录原因。
3. 实施最小完整改动，不做无关重构。
4. 运行该切片测试，再运行相邻协议、路由或配置恢复测试。
5. 完成后运行全量验证并记录实际输出，不接受“应该可以”。

最终必须通过：

```bash
swift test
bash macos/build_app.sh
git diff --check
codesign --verify --deep --strict dist/AutoRoute.app
```

还需完成本文规定的 HTTP 安全用例、配置迁移用例、首次启动 UI 手测、Agent 接入/恢复手测和真实 A/B 验证。依赖开发者证书、公证凭据、GitHub 发布权限或真实模型额度的步骤可以实现自动化并给出操作文档，但必须标为 **DONE-BUT-UNVERIFIED**，不得宣称已执行。

## 4. 架构与兼容性原则

- `AutoModelCore` 负责认证、配置迁移、策略、预算、指标和报告等可测试逻辑；SwiftUI 只负责展示和收集用户意图。
- HTTP 请求先经过统一边界校验，再进入具体 endpoint handler；不得在每个 handler 中复制不一致的认证逻辑。
- 新配置字段必须提供确定性默认值和解码测试。旧配置缺失字段时不得崩溃或静默清空用户设置。
- 供应商 API Key 与本地访问令牌分开存储；令牌不得出现在历史、日志、收据、导出文件或 Git 中。
- 默认不返回 CORS 授权。非浏览器客户端不需要 CORS；如确有浏览器客户端，后续只能使用显式 Origin allowlist，不能恢复通配符。
- 本地指标只保存计数、时间戳、耗时和费用等聚合数据，不保存提示词、代码、响应正文或令牌。
- A/B 报告区分 `auto` 与固定基线模型，保存配置版本、模型 ID、时间、重试、用量来源和质量评估方法；无质量评估时只能报告成本与性能，不能声称成功率不下降。

## 5. 优先级与交付规则

实施顺序为 P0 → P1 → P2，但每个优先级内优先做能验证架构风险的垂直切片：

1. 先完成配置迁移与 HTTP 认证边界，因为它们影响后续 Agent 接入和前端验收。
2. 再完成首次启动到真实外部代理请求的闭环，避免只做 UI 而没有可用链路。
3. 预算和 A/B 必须先定义计量口径，再实现 UI。
4. 文档、CI 和发布自动化以实际行为为准，不得描述不存在的功能。

所有新用户可见文案使用清晰的中文，并在英文文档中提供对应快速开始；不出现无依据的“最佳”“零成本”“成功率不下降”等营销承诺。

### P0.2 正文记录默认关闭并安全迁移

**行为定义**

- 新安装：`recordRequestBody=false`，请求/响应正文不写入历史。
- 旧配置：显式存储的 `true` 保留；字段缺失时使用 `false`，不得因新增字段导致整份配置解码失败。
- 用户在设置中主动开启时，展示清晰影响说明；关闭后不再记录新正文，但不得未经确认删除既有历史。
- 导出的脱敏收据、日志和指标继续排除正文与所有凭据。
- 关闭正文记录时，上游错误正文也不得进入 history、供应商/模型健康备注或导出；持久化只保留固定错误类别与 HTTP 状态。客户端可收到脱敏后的详细错误，开启正文记录后才允许持久化详细错误。

**测试**

1. 无该字段的旧 JSON 能解码且默认 `false`。
2. 显式 `true` 和显式 `false` 均按原值保留。
3. 默认配置完成一次真实代理调用后，持久化记录不包含请求或响应正文。
4. 用户主动开启后才记录；再次关闭后新记录恢复无正文。
5. 既有 `CallRecord`、Keychain 和配置恢复测试保持通过。

### P0.3 建立统一本地 API 安全边界

**威胁模型**

仅监听 loopback 不能防止恶意网页向 `127.0.0.1` 发请求，也不能防止 DNS Rebinding、跨域读取收据或浏览器触发策略修改。需要同时处理 Host、Origin、CORS 和认证，而不是只隐藏端口。

**认证与授权**

- 首次启动生成至少 256 位随机的本地 API token，保存在 macOS Keychain；供应商密钥继续使用各自独立条目。
- `/v1/models`、三种对话端点和全部 `/api/local/*` 均要求本地 token。接受标准的 `Authorization: Bearer <token>`；Anthropic 兼容客户端可使用 `x-api-key`。
- token 比较不能提前因字符差异退出；错误响应不附带 token。
- 未认证或错误 token 返回 `401` 与结构化错误；`/health` 可保持匿名，但只能返回最小健康状态，不泄露模型、供应商、策略、历史数量或档位。
- Keychain token 读写失败时只能使用每次启动重新生成的临时凭据作为安全回退；UI 必须显示阻断性警告，禁止自动启动代理和写入 Agent 配置，直到显式重试持久化成功。不得让用户误以为 Agent 配置可长期复用。
- 设置与首次引导提供复制 token、复制 Base URL、复制已脱敏 curl 的能力；Agent 一键配置必须写入或更新本地 token。恢复使用原始备份、当前文件和受管数据三方定向移除，保留接入后新增的 provider/MCP/env/设置，不整文件覆盖。
- 备份清单 manifest 读取或解码失败必须明确阻断 apply/restore；检测到已有 `.bak` 时绝不能重新写入覆盖。恢复失败不得误报“无备份”。
- 这是有意的安全迁移：旧占位 key 不再默认可用。升级说明必须指引用户重新一键接入或更新手动客户端，不得保留永久的不安全兼容开关。

**Host、Origin 与 CORS**

- Host allowlist 仅允许实际监听的 loopback 地址与端口；非法 Host 返回 `403`。
- 带 `Origin` 的请求仅允许明确 loopback 来源；其他来源返回 `403`。无 Origin 的原生/CLI 客户端可正常认证访问。
- 默认响应不包含 `Access-Control-Allow-Origin`，尤其禁止 `*`；OPTIONS 不能绕过 Host、Origin 或认证策略。
- `/api/local/receipts`、策略切换、模型发现、档位修改等敏感接口必须独立通过认证测试。
- 移除 `NSAllowsArbitraryLoads`，保留并验证最小所需的 `NSAllowsLocalNetworking`。

**必须先红后绿的用例**

| 用例 | 预期 |
|---|---|
| 无 token 请求 `/v1/models` | 401，不返回模型目录 |
| 错误 token 请求 `/v1/chat/completions` | 401，不调用上游 |
| 正确 Bearer token | 按既有逻辑执行 |
| Anthropic 客户端正确 `x-api-key` | 按既有逻辑执行 |
| 有效 token + 恶意 Host | 403 |
| 有效 token + 非 loopback Origin | 403 |
| 匿名读取 receipts 或修改策略/档位 | 401，状态不变 |
| OPTIONS | 不返回通配 CORS，不授予未授权访问 |
| 匿名 `/health` | 仅最小健康字段 |
| 日志、历史、导出 | 均不包含本地 token |

### P0.4 可重复构建、签名、公证和分发自动化

**本地脚本职责**

- `macos/build_app.sh`：Release 构建、Info.plist、可复现目录结构、签名和基本验证。
- 无开发者凭据时允许显式的本地 ad-hoc 构建，但输出必须标注“仅本地开发，不可作为正式公证分发”。
- 配置 `DEVELOPER_ID_APPLICATION` 后使用 Developer ID 签名并执行严格验证；`AUTOROUTE_REQUIRE_DEVELOPER_ID=1` 时还必须匹配签名 `Authority`，禁止 ad-hoc 通过 Release 构建。
- CI 通过 `macos/prepare_release_signing.sh` 在临时 keychain 中导入 `DEVELOPER_ID_CERTIFICATE_P12_BASE64` 对应的证书/私钥，配置并验证 notarytool profile；`macos/cleanup_release_signing.sh` 在 `always()` 步骤清理。secret 名称只写入发布文档，真实证书、密码和 profile 内容不得进入仓库。
- 独立公证脚本通过准备好的临时 notarytool keychain profile 提交 ZIP、等待结果并 staple；本地受信任环境也可显式使用已有 profile，但不得把 Apple ID、密码、Team ID 或 profile 内容写入仓库。
- 打包脚本生成带版本的 `AutoRoute-<version>.zip` 和 SHA-256，Release 文档给出准确命令。
- Homebrew 以 cask 模板和生成脚本落地，版本、下载地址与 SHA 必须由真实 Release 产物生成；未发布前不得宣称 `brew install` 已可用。

**GitHub Actions**

- PR/push CI：Swift 测试、Release 构建、格式差异检查。
- tag Release：仅在所需签名/公证 secrets 完整时发布正式资产；缺少凭据应清楚失败或跳过发布，不能把 ad-hoc 包冒充正式版。
- workflow 权限最小化，第三方 action 使用不可变版本；优先使用 GitHub 预装 `gh` 发布，减少不必要依赖。
- CI 不访问用户真实 Keychain、API Key、Agent 配置或真实上游。

**验收与外部边界**

本地必须验证脚本语法、构建、产物结构、版本、SHA 和签名。Developer ID 签名、notarytool、公证后 `spctl -a -vv`、Homebrew 安装、GitHub Actions 实际运行与 Release 上传需要相应凭据/推送授权，未执行时统一标记 `DONE-BUT-UNVERIFIED` 并列出操作步骤。

## 7. P1：首次成功、精细策略与可信效果报告

### P1.1 将首次引导改成一条可完成的垂直链路

**目标流程**

```text
欢迎/隐私说明
  → 用户主动发起本机发现与测活（或手动添加供应商）
  → 展示健康模型并自动推荐低/中/高档，允许修改
  → 选择省钱/均衡/质量策略
  → 选择已检测 Agent，一键备份并接入
  → 通过真实 127.0.0.1 HTTP 代理发送验收请求
  → 展示实际模型、路由原因、TTFT、Token、费用和回退收据
```

**实现要求**

- 复用现有 `OnboardingView`、自动发现、档位配置、Agent 备份/恢复和测试台能力，不另建平行业务流程。
- 自动发现和测活只能由用户明确点击触发；说明会读取哪些本机配置、会向上游发送轻量测活请求。
- 每一步只有一个主按钮，同时保留高级配置入口；已完成步骤可返回修改，不能清空用户已有选择。
- 验收请求必须通过真实 HTTP socket 访问本地代理并携带本地 token，不能直接调用 engine 内部方法来伪装端到端成功。
- 真实验收会产生上游费用，按钮和确认文案必须明确；使用模拟上游时标记为“演示链路”，不能计入真实路由成功指标或成本节省。
- `hasCompletedOnboarding` 只能在真实外部代理请求成功或用户明确跳过后设置；跳过不删除配置，可从设置继续。
- 端口冲突、无健康模型、认证失败、额度不足、超时、协议不兼容均显示下一步动作，而不是只显示原始错误。
- Agent 未安装时提供手动 Base URL、token、模型名和复制 curl 的等价路径。

**UI 手测**

1. 在隔离 HOME/测试持久化目录中从空配置启动，确认默认无正文记录且无法匿名调用。
2. 使用本地模拟上游完成演示链路，确认其不计为真实节省。
3. 使用至少两个真实可用模型完成发现、档位、策略、Agent 接入和真实验收。
4. 关闭主窗口后代理仍可用；重新打开可查看刚才收据。
5. 断开 Agent 后恢复原配置；重复接入/恢复不会累积重复片段或破坏其他供应商配置。
6. 分别模拟端口占用、错误 key、429、超时，确认引导能定位到可执行修复动作。

### P1.2 Agent 身份与策略解析

**身份要求**

- 一键接入的已知 Agent 必须携带稳定、可测试的身份，不得依赖容易变化的完整 User-Agent 字符串猜测。
- 优先复用客户端必定提供的模型字段或受控接入配置；如使用 `auto/agent/<agent>` 别名，必须在 `/v1/models`、文档和 Agent 配置中一致，并为未知别名返回明确 400。
- 可选 `X-AutoModel-Agent` 仅作为显式集成能力；身份用于选择策略，不构成安全授权边界。
- 手动客户端和旧配置继续使用全局策略；升级不能使现有 `auto`、`auto/low|medium|high` 或具体模型 ID 改变含义。

**策略优先级**

1. 认证、Host/Origin、安全约束和预算硬性限制。
2. 具体模型 ID 直连语义。
3. 用户显式档位与请求硬约束（tools、vision、context、价格、client effort）。
4. 已识别 Agent 的策略与档位覆盖；未配置时继承全局策略。
5. 既有子任务/effort 路由、会话粘性、阶段升降档、健康度、冷却与有序回退。

任何覆盖都不能绕过 tools/vision/context 等硬约束。收据需记录身份来源、命中的 Agent profile、最终策略和覆盖原因，但不记录令牌。

**测试**

- 每种受支持 Agent 的一键配置都产生预期身份，并能通过真实代理解析到对应 profile。
- 未知身份、伪造/旧别名、大小写和空值行为确定。
- 全局策略、Agent 覆盖、显式档位和具体模型的优先级有表驱动测试。
- 多 Agent 并发请求不会串用策略、会话粘性或预算。
- 既有路由测试全部保持通过。

### P1.3 按 Agent 与月度预算控制

**配置与口径**

- 支持全局和按 Agent 的可选月度预算；未设置表示不限制。
- 月份按本机时区的自然月计算，持久化周期标识，跨月后自动开始新周期，不删除历史收据。
- 预算以用户配置单价和上游实测 usage 计算；本地估算 usage 单独累计并标记。未配置单价的消费显示为 `unpriced`，绝不能按 0 元计入。
- 明确标记为 demo 的模拟消费不得进入 measured、estimated 或 unpriced，也不得触发全局或 Agent 的 `429`；真实与旧版来源无法判别的记录继续计量。
- 预算累计使用独立持久化 ledger（周期 + Agent + 口径），不以最多 500 条的 UI 历史为计量来源。旧配置没有 ledger 时从现有历史回填；清空历史必须同步清空 ledger。
- `MonthlyBudgetSettings.warningThreshold` 是全局和 Agent 预警的唯一权威阈值；`MonthlyBudgetLimit.warningThreshold` 仅为兼容旧 JSON 保留，不参与判断。
- 预警状态是纯逻辑，必须包含周期、上限、已计量金额，并区分未设置不限、阈值前、恰好达到阈值、达到硬上限；实测、估算、未定价口径保持不变。达到预警阈值时 UI 显示可见提示但不阻止请求；只有达到硬上限时，新请求才在调用上游前返回 `429`，错误码为 `budget_exceeded`，并显示当前周期、上限和已计量金额。
- 重试产生的实际上游费用也计入；失败但未产生上游用量的请求不能虚构费用。
- 预算控制是本地计量保护，不宣称能替代供应商账单。并发在途请求、上游延迟 usage 或价格变更可能造成超支，UI 与文档必须说明；不得静默删除历史来“修复”预算。

**测试**

1. 月初、跨月、时区和应用重启后的周期一致。
2. 全局与 Agent 预算分别累计，互不误扣。
3. 达到上限前最后一条允许、下一条阻止且上游调用次数不增加。
4. 实测、估算、未定价、重试和失败请求分别按口径统计。
5. 并发请求不出现负余额、重复扣费或数据竞争；若有最大超支边界，测试并记录。
6. 预算错误响应兼容 OpenAI/Anthropic 错误结构且不泄露请求正文。

### P1.4 可复现 A/B 与报告导出

**运行模型**

- 用户选择固定基线模型与 `auto` 策略，运行同一组版本化样例；两边保持消息、工具、温度等参数一致。
- 测试台只保留可审计的交错 A/B runner。不得提供普通单次请求中的隐式基线调用旁路；所有付费基线请求必须走同一 runner，产生独立 CallRecord，并经过预算、usage 与重试计量。
- 每个用例使用独立会话标识，避免粘性、缓存或前一轮升降档污染对照；需要测试缓存时必须另设实验组。
- 保存样例版本、策略版本、策略名称、Agent、非敏感请求参数/配置、模型、时间、重试、路由耗时、TTFT、总耗时、输入/输出 Token、usage 来源和费用口径。
- 至少支持重复运行与交错顺序，避免把网络波动直接归因于路由；报告中展示样本数，单一样本不得给出笼统百分比结论。实际 runner 必须为每次调用生成独立 sessionID，并保证两边除模型与会话标识外参数一致。
- 成本汇总不能按最终 attempt 的 usage 来源给整对费用分类；必须逐 attempt 拆分实测与本地估算，只比较双方同口径成本，早期估算重试不得混入实测差值。真实 A/B 指标只接受双方均为 `upstreamReported` 且没有估算重试的配对。
- 质量评估必须显式选择：可执行检查器、人工盲评或“未评估”。未评估时报告只包含成本/延迟，不显示“成功率不下降”。
- JSON 导出包含完整非敏感配置与逐样本结果；汇总视图区分实测对照、历史估算和缺失数据。CSV 如提供，只能由同一报告模型生成，不能另算一套口径。
- 提供小型公开样例和运行说明，真实模型结果由使用者生成；仓库不得提交伪造的“官方成绩”。

**验收**

- 用本地可控上游制造不同延迟、usage、失败与重试，验证每条 A/B 记录和汇总数值。
- 基线为固定模型，实验组确实经过路由器；两边请求参数除会话标识外一致。
- 缺少 usage 或价格时显示缺失/估算，不产生确定节省结论。
- 报告导出后重新导入或解码仍保持同样汇总，且不包含 API key、token、提示词正文（除非用户明确选择包含）。
- 至少运行一次真实上游小样本 A/B 并保存原始报告；没有可用额度时标为未验证，不编造结果。

### P2.3 本地优先的产品指标

**指标定义**

- 首次成功路由率：本地引导开始后，首次真实外部代理请求成功的比例；演示模拟请求单独计数。
- 7 日活跃：本机最近 7 天发生真实外部代理路由的天数和最近使用时间。单用户数据不能冒充项目级 cohort retention。
- 路由附加延迟：真实外部代理收据中的路由判断耗时，展示 p50/p95 与样本数。
- 故障恢复率：真实外部代理发生可重试上游失败后，经备选模型成功且未重复产生用户可见内容的比例。
- 实测成本节省：仅来自来源明确、非 demo 的真实 A/B（允许 testBench 的 A/B 执行）或有明确口径的历史对照，缺失价格/usage 单独列示。
- 真实路由活跃/延迟样本与 A/B 成本对照样本必须分开定义：testBench A/B 可进入成本指标，但不能混入 7 日外部路由活跃或路由延迟。

**隐私与实现**

- 优先从现有收据派生指标；只为引导漏斗补充最小事件，不记录提示词、代码、响应、模型消息、token 或稳定广告式标识符。
- 数据仅本地保存，用户可查看、清空和主动导出聚合 JSON；默认不上传，也不设置隐蔽后台任务。清空历史、指标和预算 ledger 必须原子协调：持久化失败时抛出并在 UI 显示，不能清空内存后仍显示成功。
- 导出包含 `schemaVersion`、时间范围、指标定义版本和样本数，便于维护者接收用户自愿分享的匿名聚合。
- 项目级 Star、下载、Issue、贡献者和 Release 数据由维护者从平台读取，不能通过本地客户端伪造。

**测试**

- 空历史、单一样本、跨月、失败重试、无 usage、无价格和重复事件的计算正确。
- 清空历史后指标按明确规则重置；删除操作需要用户确认。
- 导出文件通过敏感字段检查，网络测试证明指标功能本身不发起额外请求。
